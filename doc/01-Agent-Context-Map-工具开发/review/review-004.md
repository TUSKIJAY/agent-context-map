## 整体判断

## 总体评价

本轮为修订审，基准为 review-003，核查边界仍为 ACM-MD 规范（文档 03，内容未变）。与前几轮不同：review-003 已是无遗留项的 approve，因此本轮不是"修复核对"，而是对 v0.2.4 一次较大范围**新增内容的回归审**。v0.2.4 在版本号上只从 v0.2.1 跳到 v0.2.4，但实质是一次重大范围扩展，新增了三块能力：① 把定位从"软件需求图谱"放宽为"通用逻辑上下文图谱"，通过 Domain Profile/模板适配研究、写作、投标、决策等场景；② 本地持久化与"可恢复工作现场"（最近打开、自动草稿、关闭恢复、源文件丢失兜底）；③ 把最终交付形态固定为 Windows 绿色版 exe，并新增 P5 打包验收与配套 SOP。

最关键的协议忠实往返维度，v0.2.4 处理得当：受控词表（7.0）、ChangeSet（7.4）、关系推断表（6.7）与校验规则（4.1 I）相对已批准的 v0.2.1 完全未变；新增的通用化机制被刻意限制在"只改 UI 显示名、不改底层 NodeType/RelationType、不写入导出 ACM-MD"（6.5、7.8、8.6、10.4、风险8），6.5 映射表左列也只用了规范第 7 节的 12 个合法类型；持久化层显式与协议格式解耦，并强调"自动保存不得损坏原 ACM-MD 文件"（4.1H、10.2、风险7）。也就是说，这次扩展没有在协议一致性上引入新缺陷，前三轮修复的成果（尤其 7.7 的 id 策略，现已写入 P0 验收 L863）均完整保留。值得肯定的是，扩展同时补了风险 6/7/8 覆盖新范围的失效模式，并把 Tauri 桌面骨架与 release exe 冒烟前置到 P0 以降包装风险。

回归审发现的唯一一项中等问题是范围层面的：MVP"必须实现"与"第一版成功"的口径随这次扩展显著变大（协议闭环之外又叠加了持久化子系统、绿色版打包与 6 套模板）。这不是正确性缺陷，方案也已把新范围分摊到 P0–P5，故不构成 revise；但建议明确把"协议往返闭环"指定为可独立交付的核心，避免被更大的工作台/打包面所拖累。其余为轻微与未验证项。据此裁定 approve，置信度 medium——协议侧已对照文档 03 验证干净，但本次扩展把更多成败因素（Tauri 打包/WebView2、外部工程 SOP、P4 集成）推到了核查边界之外。

## 问题清单

### 严重问题

无。本次扩展未在协议一致性或执行正确性上引入根本性问题。

### 中等问题

1. **MVP 与"第一版成功"范围随扩展显著放大，建议显式区分"可独立交付的协议核心"与"工作台/打包增量"** [修订引入]
   - 位置：4.1（新增 H 本地存储与恢复）、5.3 打包、6.5 Domain Profile、9-P5、12 成功定义
   - 问题描述：原 MVP 的核心价值是 ACM-MD 协议往返（导入→编辑→导出 diff）。v0.2.4 把"必须实现"扩展为同时包含完整持久化子系统、绿色版 exe 打包、6 套领域模板，且 12 节"第一版成功"已把"绿色版 exe 中成立 + 关闭重开恢复现场 + 通用模板不限于软件工程"全部并入核心闭环。范围大致翻倍。
   - 影响范围：并非正确性缺陷（扩展是起草者的合理产品决策，且已分摊到 P0–P5），但会放大第一版交付风险：协议闭环这一最具确定性、也最依赖文档 03 的核心，可能被持久化/打包/模板这些依赖第三方运行时与外部 SOP 的工作捆绑，延后可验证的里程碑。
   - 改进建议：在里程碑或成功定义中显式声明"P0–P2 的协议往返闭环可独立验收"，把持久化（P1）、模板（P3）、绿色版打包（P5）作为并行增量而非协议闭环的前置阻塞；或为"第一版成功"区分"协议核心成功"与"工作台完整成功"两档，便于在工期紧张时优先保住协议闭环。

### 轻微问题

1. **版本号低估了变更量级，缺少变更记录** [修订引入]
   - 位置：第 3 行（v0.2.1 → v0.2.4）
   - 问题描述：本次是定位、交付形态、子系统级的扩展，却以补丁号呈现，且文中无 changelog。下游 Agent 与评审者难以从版本号判断"产品定义本身已变化"。
   - 改进建议：升为次版本（如 v0.3）并附一段变更摘要，至少标注"新增通用化/持久化/绿色版交付"。

2. **diff 基线的存储位置存在双写歧义** [修订引入]
   - 位置：5.2（`snapshots/<doc_id>/<timestamp>.json` 用于"恢复或 diff 基线"）与 7.8（`DraftRecord.base_snapshot` 内联）
   - 问题描述：基线快照同时出现在草稿内联字段与 snapshots 目录两处，未说明哪个是 diff 的权威基线、二者如何同步。
   - 改进建议：明确权威基线来源（建议以 base_snapshot 为运行时基线，snapshots/ 仅作历史恢复点），避免实现期出现两份不一致基线。

3. **domain_profile 仅本地保存，导出后再导入会丢失模板上下文** [修订引入]
   - 位置：7.8 L751、6.5
   - 问题描述：为保护协议往返，domain_profile 不写入导出 ACM-MD。代价是：导出的 .md 被他人或 Agent 重新导入时，模板显示上下文丢失，回落为通用显示。
   - 改进建议：此为合理的保守取舍，可保留；但建议在文档中点明这一取舍。若希望模板随文档走且不破协议，可评估写入 `meta` 的非规范提示键（规范第 5 节 meta 与本 plan GraphMeta 的 `[key: string]: unknown` 允许未知键，Agent 可忽略），作为后续可选增强。

以下为超出核查边界（仅文档 03）或需实测的事项，多数由本次扩展新引入：

- **绿色版 exe / `--no-bundle` 构建行为**：5.3 断言 `npm run tauri:build -- --no-bundle` 产出"可覆盖的 release exe"且跳过 MSI/NSIS。该命令行为属第三方工具链，文档 03 无法证实，需 P0"release exe 构建冒烟"实测确认。
- **Windows"绿色版/portable"自包含性**：Tauri 桌面应用通常依赖系统 WebView2 运行时，"绿色版 exe"是否在无 WebView2 的环境中可双击运行，需实测验证；建议在 P0/P5 明确 WebView2 依赖与兜底（运行时检测或引导安装）。**未经核查**。
- **外部工程 SOP 引用**：5.3 以"Markdown 文档审阅标注工作台"的绿色版 exe 验收方式为蓝本，该工程及其 SOP 不在核查资料内，**未经核查**；建议确认其构建产物形态确与本 plan 假设一致。
- **P4 与"任务拆解大师"的真实集成闭环**：生成端能否产出可无报错导入的 ACM-MD 位于文档 02，超出本次核查边界，**未经核查**，需端到端实测。
- **原型性能**（10.5，100 节点/200 边）：React Flow 实际渲染/拖拽性能需实测。
- **被审文档中未被核查资料（03）覆盖的事实性声明范围**：① 第 5 节技术栈/打包链（Tauri、React Flow、Dagre/ELK、Vite、SQLite、`--no-bundle`、WebView2）的具体行为；② 5.3 引用的外部工程；③ 一切关于"任务拆解大师"的能力声明（3.3、9-P4、12）。

## 裁决理由

选择 **approve**：v0.2.4 是一次较大范围扩展，但回归审表明它没有在最关键的协议忠实往返维度引入任何新缺陷——受控词表、ChangeSet、推断表、校验规则相对已批准的 v0.2.1 未变，新增的通用化与持久化被严格隔离在协议之外（不改底层类型、不写入导出文档、不损坏源文件），前三轮修复成果完整保留并已写入 P0 验收。新增内容内部基本自洽，并配以风险 6/7/8 与 P0 前置打包冒烟等缓解。唯一的中等问题是范围放大带来的交付风险，属可在执行阶段通过里程碑显式解耦自然消化的范畴，不构成 revise；轻微问题均为可选优化。按方案评审标准"方案可行、无严重问题、中等问题可在执行阶段解决"，满足 approve。

置信度 medium 而非 high：协议侧已逐项对照文档 03 验证为干净，但本次扩展把更多成败因素推到核查边界之外——绿色版 exe 的构建与 WebView2 自包含性、外部工程 SOP、P4 集成闭环都需实测或补充核查资料。换言之，未验证面随扩展而扩大。建议执行时：把"协议往返闭环（P0–P2）"作为可独立验收的核心优先保住；P0 的 release exe 冒烟一并验证 WebView2 依赖与 `--no-bundle` 实际产物；并把版本号与变更记录补齐，便于下游追踪产品定义的变化。
