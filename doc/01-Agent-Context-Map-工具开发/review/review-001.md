# 交付物评审意见

**审核对象**：01-Agent-Context-Map-工具开发Plan.md

## 整体判断
**裁决**：revise
**置信度**：medium

## 总体评价

这份 plan 在产品定位与方向判断上是扎实的。它准确抓住了工具的核心张力——"交互层自由 / 语义层严格"，并据此给出了合理的模块切分（Parser / Schema / Graph Store / Canvas / Relation Inference / Diff / Export）、可落地的技术选型，以及一条朝"闭环可用"收敛的 P0–P4 里程碑。把"第一版成功"定义为闭环而非功能数量，是克制且正确的判断。

但本工具存在的唯一理由，就是与 ACM-MD 协议的**忠实往返**（导入规范文档 → 编辑 → 导出规范文档 / diff）。把 plan 的数据契约逐字段对照 ACM-MD 规范（文档 03）后，发现 plan 的数据结构与协议在若干处**不是对齐而是相反或缺失**：ChangeSet 把规范定义为可选的 6 个变更数组写成了必填，GraphDocument 漏掉了规范的 `validation` 顶层字段，受控词表（节点/关系/状态枚举）在 plan 内从未锚定、而唯一一处具体的关系枚举（6.5）既与规范不一致、又与 P3 验收标准自相矛盾。这些不是"执行阶段自然会消化"的中等问题，而是若按字面实现就会让导入器拒绝规范合法文档、让校验器和关系推断引擎建立在错误词表上的根本性正确性问题。

因此判定为 revise 而非 approve：方向无需重做，但数据契约必须先与规范对齐再进入执行。也不构成 reject：全部问题均可在不推翻设计的前提下修订。需要说明，本次核查边界仅为 ACM-MD 规范（文档 03），与"任务拆解大师"的集成闭环（P4）及技术栈运行时可行性均无法从现有资料验证，详见未验证项——这也是置信度定为 medium 的原因。

## 问题清单

### 严重问题

1. **ChangeSet 变更数组的可选性与规范相反，会破坏 ACM-MD 往返导入**
   - 位置：plan 7.4 ChangeSet 类型 ↔ 规范 13.2 changes 字段说明
   - 问题描述：规范 13.2 明确把 `added_nodes / modified_nodes / removed_nodes / added_edges / modified_edges / removed_edges` 六个字段全部标为"否（可选）"，只有 `change_set_id / base_doc_id / summary` 必填。但 plan 7.4 的 `ChangeSet` 把这六个数组全部写成了非可选字段（无 `?`）。
   - 影响范围：Schema 模块（6.2）以此类型为依据生成 Zod 校验。若按字面实现，导入器会拒绝任何省略了空变更数组的合法 ACM-MD；而"任务拆解大师"按规范产出的 changes 很可能只携带实际发生的变更类别。结果是 P4 的核心闭环（"任务拆解大师生成的图谱能无报错导入"）在协议层就被破坏，且失败表现为"规范合法文档被判非法"，最难排查。
   - 改进建议：将六个变更数组改为可选；导入时缺省归一化为空数组，导出时按规范可省略空字段。同时在 Schema 模块验收用例中加入"仅含部分变更类别的 changes 块"的正例。

2. **受控词表未在 plan 内锚定，唯一的关系枚举与规范不一致且与 P3 验收自相矛盾**
   - 位置：plan 7.2/7.3（`NodeType`/`NodeStatus`/`RelationType`/`EdgeStatus` 均未定义）、6.5 关系推断表、9-P3 验收 ↔ 规范 7/8/10/11，校验 15.1.8–15.1.9
   - 问题描述：
     (a) plan 全文未列出节点类型、节点状态、关系类型、边状态的合法取值，7.2/7.3 直接引用 `NodeType` 等类型却无定义；规范 7.1 有 12 种节点类型、8 有 4 种状态、10.1 有 10 种关系类型。
     (b) plan 内唯一具体枚举关系的地方是 6.5 推断表，但它相对规范 11 既不完整（缺 Goal→Task、Module→Page、Feature→Feature、Constraint→Module、Risk→Module、Decision→Question 等行）又不一致（plan 写 "Question→Feature needs_validation"，规范是 "Question→任意类型"；plan 写 "Decision→Feature impacts"，规范是 "impacts / replaces" 且另有 "Decision→Question answers"）。
     (c) 由此产生内部矛盾：P3 验收（plan 504 行）要求"Feature → Feature 给出候选关系"，但 plan 任何地方都没有 Feature→Feature 规则，规范 11 反而定义了该规则。即 plan 承诺了一个自身规则集无法支撑的验收项。
   - 影响范围：节点/边 type 必须在枚举内是规范 15.1.8–15.1.9 的 **Error 级**校验规则。词表未锚定或取错，会同时让校验器（6.2/4.1H）和关系推断引擎（6.5）这两个核心模块建立在错误基线上；6.5 与 P3 的矛盾会在实现到 P3 时暴露为"按计划做却无法通过自己的验收"。
   - 改进建议：在 Schema 模块或数据结构章节内显式锚定四套受控词表，并声明"以 ACM-MD 规范第 7/8/10 节为唯一来源"；把 6.5 升级为与规范 11 完整一致的推断规则表（含 Feature→Feature 的多候选），消解与 P3 的矛盾；若 6.5 仅作示例，也需补一句"完整表以规范为准"并保证示例不与规范冲突。

### 中等问题

1. **GraphDocument 缺少规范的 `validation` 顶层可选字段，往返会丢失**
   - 位置：plan 7.1 GraphDocument ↔ 规范 4.2/4.3
   - 问题描述：规范 4.2 把顶层可选字段列为 `layout / changes / validation` 三项，plan 7.1 只有 `layout?` 与 `changes?`，漏了 `validation`。
   - 改进建议：在 GraphDocument 加上 `validation?` 字段并在导入/导出时原样透传，避免对携带 validation 的文档做有损往返；若决定 v0.1 暂不使用，也应在文档中显式说明"读入后保留、不解释"。

2. **自动布局既列为 MVP 必做又列为 P3 交付，且无 layout 文档的早期渲染缺口未交代**
   - 位置：plan 4.1B（"支持自动布局"列入必须实现）、9-P3（"完成自动布局"）↔ 规范 18.5（"layout 缺失时自动布局"）
   - 问题描述：同一能力在 4.1B 被列为 MVP 必做、在 P3 才交付，时点矛盾。规范 18.5 要求工具在 layout 缺失时自动布局，而规范 17.7 指出生成方可省略 layout——意味着导入无 layout 的文档会很早出现（React Flow 需要节点坐标才能渲染）。
   - 改进建议：明确自动布局的落地时点。建议 P0/P1 即提供一个最小布局兜底（哪怕简单网格/Dagre 默认），把 P3 的"自动布局"收窄为"布局质量优化"；或显式声明 P3 前只支持带 layout 的文档，并据此调整 P0 验收样例。

3. **"工具内不调用 AI"约束下，summary / agent_instructions 的本地生成机制未定义**
   - 位置：plan 4.1F、7.4、11-风险3 ↔ 3.3（本地优先，编辑环节不调用 AI）
   - 问题描述：4.1F 与风险3 要求每次导出生成面向 Agent 的 `summary` 与 `agent_instructions`，但 3.3 明确禁止工具内调用 AI，plan 未说明在无 AI 前提下这两段自然语言如何产生（模板拼装？用户手填？）。这恰是 diff 对 Agent 可用性的关键环节。
   - 改进建议：明确生成策略。建议采用确定性模板（基于结构化 diff 字段拼装人类可读摘要），并说明 `summary`/`agent_instructions` 是模板生成还是允许用户编辑；同时澄清在纯模板下 P4 验收"Agent 读取 diff 后准确继续工作"主要依赖结构化字段而非自然语言。

4. **新建文档 / 新增实体的 id 与 doc_id 生成策略未定义，与"id 稳定"核心原则脱节**
   - 位置：plan 3.2、4.1C、8.1（新建）、10.2 ↔ 规范 14（id 命名规范）
   - 问题描述：plan 反复强调"id 必须稳定、不依赖 title"（3.2、10.2），却未说明新建空图谱的 `doc_id`、以及画布上新增节点/边/changes 的 id 如何生成。规范 14 给出了按类型前缀（`goal_`/`module_`/`edge_` 等）的命名约定，plan 未引用。
   - 改进建议：定义 id 生成策略（建议遵循规范 14 的前缀 + 单调序号或 uuid），并说明"新建"动作如何产出满足必填字段的最小合法骨架（schema_version / doc_id / meta.title / nodes[] / edges[]）。

5. **MVP 校验只覆盖 Error 级规则，规范 15.2 的 8 条 Warning 规则一条未纳入也未声明延后**
   - 位置：plan 4.1H ↔ 规范 15.2
   - 问题描述：4.1H 列出的校验项基本对应规范 15.1 的 Error 级规则，但规范 15.2 定义的 8 条 Warning（核心 Goal 无出边、Risk 无影响对象、Question 无待验证对象、confidence/source 缺失、Feature 无所属 Module、多 Goal 未建关系、suggested 未确认）在 plan 中一条都没有；虽然 11-风险2 提到"校验分 warning 和 error"，但未落到具体规则。
   - 改进建议：将规范 15.2 的 Warning 规则纳入校验模块，或在 4.2"第一版暂不做"中显式声明哪些 Warning 延后，避免"提到了分级却没有 warning 内容"的空挂。

6. **自动推断生成的边状态未明确为 suggested，存在违反规范的风险**
   - 位置：plan 8.3（"若只有一个强匹配关系，直接创建"）、4.1D ↔ 规范 11、17.5
   - 问题描述：8.3 描述拖线后对强匹配关系"直接创建"，但未说明创建出的边 status 为何值。规范 11 要求工具生成的未确认关系标 `suggested`，17.5 明确"不要把用户未确认内容标记为 confirmed"。若直接创建为 confirmed 即违规。
   - 改进建议：明确自动推断边一律以 `suggested` 落库，待用户确认后再转 `confirmed`；Inspector/diff 中体现该状态区分。

### 轻微问题

1. **4.1F 的 diff 字段枚举遗漏 change_set_id / base_doc_id，与 7.4 不一致**
   - 位置：plan 4.1F ↔ 7.4
   - 改进建议：在 4.1F 的字段清单补上 `change_set_id` 与 `base_doc_id`，与 7.4 ChangeSet 保持一致。

2. **confidence 未注明取值范围**
   - 位置：plan 7.2/7.3 ↔ 规范 6.3/9.3（confidence 0 到 1）
   - 改进建议：在数据结构或 Schema 校验中注明 confidence ∈ [0,1]，由 Zod 强约束。

3. **removed/modified 的 reason 在编辑 UX 中无捕获入口**
   - 位置：plan 8.2、7.4 ↔ 规范 13.1（removed_nodes 含 reason）
   - 改进建议：删除/修改关键节点时提供可选的 reason 输入，以便 changes 携带删除/修改原因；若 v0.1 不采集，说明 reason 留空策略。

4. **"定位唯一的 acm 代码块"比规范"推荐一个"更严格，多/零代码块行为未定义**
   - 位置：plan 4.1A ↔ 规范 2.3
   - 改进建议：定义出现 0 个或多个 acm 块时的解析行为（报错并指明位置 / 取首个主块），与规范 18.3"解析失败给出具体错误位置"对齐。

5. **术语 "Agent Diff" 与规范 "changes / ChangeSet" 并存**
   - 位置：plan 4.1F、8.4 等 ↔ 规范 13
   - 改进建议：统一术语或在文档中注明 "Agent Diff" 即规范的 changes/ChangeSet，避免下游 Agent 与读者混淆。

6. **草案类型 GraphLayout / NodeFieldChange / RemovedNode 等内部结构未展开**
   - 位置：plan 7.x
   - 改进建议：属"草案"可接受；建议在进入 P2 前补全 GraphLayout（engine + nodes 坐标映射，对齐规范 12.1）与字段级变更类型，确保 NodeFieldChange 为"每字段一条"以匹配规范 13.1 的粒度。

## 未验证项

- **P4 与"任务拆解大师"的集成闭环**：plan 在 3.3、9-P4、12 节反复将"任务拆解大师能产出可无报错导入的 ACM-MD"作为成功前提，但该能力声明位于文档 02，超出本次核查边界（仅 03），**未经核查**。建议在覆盖文档 02 后专项验证生成端与导入端的端到端兼容。
- **技术栈运行时可行性**：第 5 节关于 React Flow（大规模图谱下的拖拽/渲染性能）、Dagre/ELK.js、Tauri FS API 的具体能力声明，属第三方库实际行为，文档无法证实——需原型实测。plan 也未给出目标图谱规模（节点/边量级），建议补充并据此评估画布性能。
- **画布编辑体验是否优于直接写 Markdown**（11-风险4）：需可用性测试，非文档可证。
- **diff 基线的跨会话语义**：plan 以"原始导入快照"为 diff 基线（6.3），但"保存新版 → 重开 → 再编辑"多轮循环下基线如何重置、base_doc_id 如何更新，未详述；建议明确"每次重新导入即重置基线"的规则。
- **规范 15.2 业务级 Warning 在本工具的取舍**：在中等问题5 处理前，这部分校验覆盖度无法判定。
- **被审文档中未被核查资料（03）覆盖的事实性声明范围**：① 全部关于"任务拆解大师"的能力、接口与产出格式声明（3.3、9-P4、12 节）；② 第 5 节所有第三方库/框架（Tauri、React Flow、Zustand、Zod、Dagre、ELK.js、Vite、Electron）的具体能力与适配性判断。上述均建议由协调者决定是否补充对应核查资料后再行验证。

## 裁决理由

选择 **revise** 而非 approve：本工具的根本职责是 ACM-MD 的忠实往返，而 plan 与规范（文档 03）的对照暴露出至少两处会直接损害协议正确性的严重问题——ChangeSet 变更数组可选性被写反（导入器会拒绝规范合法文档）、受控词表未锚定且唯一的关系枚举与规范不一致并与 P3 验收自相矛盾。二者都不属于"执行阶段自然消化"的范畴：若按字面进入 Schema 模块与推断引擎，会把缺陷固化为代码，并在 P3/P4 才以"按计划做却通不过自己验收/拒绝合法输入"的形式爆发，排查成本高。叠加 6 条中等问题（多数同为协议对齐/时点一致性问题），整体已达到"需起草者修订后重新送审"的门槛。

选择 revise 而非 reject：plan 的产品定位、模块切分、技术选型与里程碑编排在方向上成立，全部问题均为"与规范精确对齐"性质的可修订项，无需推翻设计。把 7.1/7.4 数据契约与四套受控词表逐一钉死到 ACM-MD 规范、消解 6.5 与 P3 的矛盾、明确自动布局时点与 summary/agent_instructions 的本地生成方式后，即具备进入执行的条件。

置信度定为 **medium**：本次评审对协议侧（plan 的数据结构、枚举、校验、changes 格式与 ACM-MD 规范的一致性）做了逐字段核对，结论依据充分；但 plan 成立的另一半——与"任务拆解大师"的集成闭环、以及技术栈在真实环境下的可行性——位于核查边界之外或需实测，无法从现有资料证实，故不取 high。
